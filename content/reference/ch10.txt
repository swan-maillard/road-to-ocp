10.1 Important classes of the Date API ☝
To machines, time is just a period that has elapsed after a predefined starting point. This point in time is called "Epoch" and is setat January 1, 1970 00:00:00.000 at Greenwich. Time at this location is called Greenwich Mean Time (GMT). The same time hasbeen adopted globally as the reference time and is also called Coordinated Universal Time or UTC for short. You can think of timeas a series of milliseconds plotted on the x-axis, where 0 is called January 1, 1970 00:00:00.000 GMT. Every millisecond elapsedsince the epoch moves you forward on this axis.Humans see time in terms of hours, minutes, and seconds of a specific day, month, and year, at a particular location. For example, to computers, the point 1735711200000 on the time line means 1735711200000 number of milliseconds haveelapsed since the epoch. But to humans, this point is actually 6AM 1st January 2025 at Greenwich. The same point in timecould also be interpreted as 1AM on January 1st 2025 in New York or 10PM on Dec 31st 2024 in Los Angeles. 
The new date/time framework is organized in the java.time package and has a lot of classes and interfaces. The following diagramshows a few important classes and interfaces of this API. Dashed boxes contain interfaces and regular boxes contain classes.
In the above diagram, ten classes are shown in bold. Even though the exam only focuses on these ten classes it is important tounderstand the framework of the related classes as well. The following is an overview of the packages and classes shown in theabove diagram.
The java.time package
This is the most important package of the date/time framework. The majority of the application programs only need the classesdefined in this package. The classes defined in this package are based on the ISO calendar system (You don't need to know thedetails of the ISO calendar system). All classes in this package are immutable and thread-safe. 
The most important aspect of these classes is that there is a clear separation between the classes that represent the machine view ofthe time and the classes that represent the human view of the time. 
Instant: This class represents the computer's view of time. As mentioned before, a computer only cares about the number ofmilliseconds that have elapsed since Epoch. That is exactly what an Instant contains. It has no notion of AM/PM or the time zone.
However, since the zero of the computer's time line has been defined to correspond to 00.00AM 1st Jan, 1970 UTC,converting an Instant to the time in the UTC time line doesn't require any other information. Thus, you can say that an Instantobject precisely corresponds to a date and time in UTC. You can create an Instant for any given amount of time elapsed sinceepoch. For example, Instant.ofEpochMilli(1735711200000L).
LocalDate/LocalTime/LocalDateTime: These classes represent just a date, a time, or a date and time without any indication of theplace for which that date/time is applicable. Think of it this way - if someone tells you that the President will address the nation at8PM on 1st Jan 2025, you can't really be sure exactly when you need to be ready to watch it because you haven't been told theplace for which this date and time is applicable. Without this information you may be too early or too late to watch the speech. Thus,you can't take the information available in a LocalDateTime object and identify a specific point on the machine time line. Youcan, at best, guess that this time is with respect to the region you are in and use that information to decide when to be ready to watchthe President's address. In that sense, it represents the date/time of the system on which the program is running. You will see severalways to create objects of these types in the next section.
ZoneId: A ZoneId identifies an area or a region, known as "Time Zone", for which precise rules for determining the date and timeof a day with respect to the UTC exist. These rules enable you to take a point on the machine's timeline, i.e., an Instant object,and determine the exact date and time in that region at that instant. Note that a ZoneId object itself doesn't contain any rule. It is justan id. JDK maintains the rules in an internal database of sorts (in ZoneRules class, actually, but you don't need to worry about it)within its standard library, which can be retrieved using this id. There are many ways to create a ZoneId object but usually, youwill see a ZoneId being created using a string of the form <area>/<city>. For example,ZoneId.of("Asia/Calcutta") or ZoneId.of("America/New_York"). If you check out the JavaDoc of theof method, you will notice that the underlying framework provided by the JDK is quite robust and can create the ZoneId from astring written in many different formats. Even so, the string used to create a ZoneId using the of method must either match anofficial time zone in the JDK's database or be in a format that correctly specifies an "offset" amount such as UTC+01:15. (Don'tworry, the format is not important for the exam). Trying to create a ZoneId for a non-existing place suchas ZoneId.of("Somewhere/Timbaktoo"); will cause a java.time.zone.ZoneRulesException to be thrownwith a message, Unknown time-zone ID: Somewhere/Timbaktoo.
ZonedDateTime: A ZonedDateTime object represents a date and time in a particular time zone. Thus, it needs two things - thenumber of milliseconds elapsed since the epoch and the ZoneId of the time zone whose time it represents. It uses the ZoneId tofetch all the rules that affect the date/time used in that zone and applies them to the show you the regional time. In layman terms, forexample, if people in a particular zone shift their clocks backward or forward on certain dates in a year (such as for saving daylight),then a ZonedDateTime object created for that zone knows those dates and the amount of shift that needs to be applied to show thecorrect time in that region at any instant. Since a ZonedDateTime pulls all applicable rules for that zone using the ZoneId, aZoneId is necessary to create a ZonedDateTime.
OffsetDateTime: - The OffsetDateTime class is a bit weird because it neither represents a local datetime nor does it representa datetime in any particular geographical region. It actually contains just two things - the number of milliseconds elapsed after theepoch and an offset amount called "zone offset", which is nothing but the amount by the which time represented by thisOffsetDateTime differs from UTC. Since an OffsetDateTime does not represent time for any specific geographical region,it does not care about any region specific rules. In a way, an OffsetDateTime object represents a date/time of an imaginaryplace that is always "offset" from the UTC by the given offset value. The offset amount is captured by an instance of theZoneOffset class, which extends ZoneId. You can actually create a zone offset of any amount like this:ZoneOffset zo = ZoneOffset.ofHoursMinutes(1, 10); //creates a ZoneOffset of 1 hour and10 minutesThe "id" of this ZoneOffset is "+01:10". Of course, you won't be able to find any "rules" for this zone because +1:10 is notan official time zone name of any region in the world but if you create a ZonedDateTime using this ZoneOffset, the time inthis imaginary place will always be 1 hour and 10 minutes ahead of UTC.
Period: Period represents a date-based amount of time in terms of days, months, and years. It has no notion of hours, minutes, andseconds.
Duration: Duration represents time-based amount of time in terms of hours, minutes, and seconds. It has no notion of days, months,or years. 
It is important to understand the difference between Period and Duration. Even though aPeriod representing 1 day is the same as a Duration representing 24 hours, both areconceptually different. Adding a Period of 1 day to a given date will only increment the daypart of the date and will not affect the time component but adding a Duration of 24 hours willadd 24 hours to the time part, which in turn, changes the day part as well. For example,adding a Period of 1 Day to the date before day light savings start date, will simply
increment the day without affecting the time. Thus, 9th March 2024 10 PM will become 10thMarch 2024 10 PM. But adding a Duration of 24 hours to the same date will change the dateto 10th March 2024 11 PM, because on this particular day, clocks were moved forward by 1hour. Therefore, 10PM + 24 hours is not 10PM but 11PM of the next day.
This package also contains two enums - Month and DayOfWeek. Month contains values from JANUARY to DECEMBER andDayOfWeek contains values from MONDAY to SUNDAY. It is better to use these enums instead of integers while creating date/timeobjects because they make the code more readable and they also let you avoid the confusion caused by indexing. For example,LocalDate.of(2024, Month.JANUARY, 10) is more readable than LocalDate.of(2024, 1, 10).
The java.time.temporal package
This package contains the base interfaces such as Temporal, TemporalAmount , TemporalUnit, TemporalField andTemporalAccessor of the Date/Time framework. These interfaces are implemented by various classes of the java.timepackage. 
Having common base interfaces for related classes allows applications to operate on the classes uniformly. For example, you canadd a Period to a LocalDate in the same way as you add a Duration to a ZonedDateTime , i.e., by calling theaddTo method on a Period or a Duration instance or by calling the plus method on a LocalDate or a ZonedDateTimeinstance. This is possible because both Period and Duration implement TemporalAmount, which declaresthe addTo(Temporal t) method and both LocalDate and ZonedDateTime implement Temporal.
The exam does not mention this package in the objectives but the whole scheme of things related to date/time manipulation is drivenby the interfaces of this package. Many of the methods that you will use while working with date/time classes are actually declaredin the interfaces of this package. 
The ChronoUnit enum of this package is particularly useful as it implements TemporalUnit and defines a standard set of unitsof date/time such as DAYS, MONTHS, YEARS, HOURS, MINUTES, SECONDS, NANOS, and WEEKS. These units are used whilemanipulating and creating date and time objects. ChronoUnit also overrides the long between(Temporaltemporal1Inclusive, Temporal temporal2Exclusive)method of TemporalUnit, which is used often tocalculate the difference between two date/time values in terms of the unit defined by the ChronoUnit instance.
The java.time.format package
This package contains helper classes for converting date/time objects to strings and for parsing strings into date/time classes.DateTimeFormatter and FormatStyle are the most used classes of this package.
10.2 Creating and using Dates ☝
None of the date/time classes have a public constructor. Therefore, it is not possible to create them using the new operator. Insteadof constructors, the new date/time API provides several other ways to create date/time objects. They can be broadly classified intotwo categories:
1. The overloaded public static factory methods named now, of, and from2. The overloaded public instance methods named with and truncatedTo
Using the static now/of/from methods
The now methods
1. The now methods returns an instance that represents the current date or time in the time line that the class is meant to represent.For example, since the LocalDateTime class represents the date and time of the system on which the program is running,LocalDateTime.now(); returns a LocalDateTime object set to the current date and current time as shown by thesystem's clock. LocalDate.now() and LocalTime.now() work similarly. OffsetDateTime.now()
and ZonedDateTime.now() do the same thing except that they also pick up the system clock's offset and time zoneinformation respectively.2. The Instant class represents the number of milliseconds elapsed since epoch and so, Instant.now() returns the anInstant object that contains the number of milliseconds elapsed since epoch as of the moment that Instant object iscreated.
The following code, that I ran on 26th Apr 2024 8:30:42 PM in India (my system's time zone is set to Indian Standard Timeaka IST, which is 5.30 hours ahead of UTC), makes this clear:
out.println(LocalDateTime.now()); //prints 2024-04-26T20:30:42.761568900 out.println(OffsetDateTime.now()); //prints 2024-04-26T20:30:42.762565600+05:30 out.println(ZonedDateTime.now()); //prints 2024-04-26T20:30:42.762565600+05:30[Asia/Calcout.println(Instant.now()); //prints 2024-04-26T15:00:42.762565600Z
The output generated by the above code shows that LocalDateTime doesn't read any offset or time zone information from thesystem's clock. OffsetDateTime reads the offset information but does not read the time zone information. ZonedDateTimereads both. 
Observe the letter z that is appended to the output of Instant.now(). It implies UTC. Also observe that the time printed byInstant.now() is 5.30 hours before local, offset, and zoned datetimes. That's because, IST is 5.30 hours ahead of UTC.
There are other overloaded variants of the now method that work on the same principle. For example, you may create aZonedDateTime that represents the current time in another time zone using ZonedDateTime.now(ZoneId zid). So, if Icall ZonedDateTime.now(ZoneId.of("America/New_York")) when my system time shows 26th Apr 2024 9PMIST, it will return the date and time representing 26th Apr 2024 11.30AM EST because US/Eastern time zone is 9.30hours behind IST. (IST is 5.30 hours ahead of UTC and EST is 4 hours behind UTC, so EST is 9.30 hours behind IST)
Since Period and Duration denote an amount of time and not a point in time, they don't have the now() method. But they dohave a static constant named ZERO, which denotes a period/duration of zero amount.
The of methodsThe of methods lets you create an object for any date or time by passing individual components of a date/time. Since there are toomany methods of this type, here are a few examples:
LocalDate ld = LocalDate.of(2024, 1, 10); //10th January 2024 LocalTime someTime = LocalTime.of(10, 53); //10.53 AM LocalDateTime ldt1 = LocalDateTime.of(2024, 1, 10, 23, 10, 14); OffsetDateTime.of(LocalDateTime.now(), ZoneOffset.ofHours(5)); OffsetDateTime odt2 = OffsetDateTime.of(2024, 1, 1, 10, 45, 50, 0, ZoneOffset.ofHours(5)ZonedDateTime zdt2 = ZonedDateTime.ofInstant(Instant.now(), ZoneId.systemDefault());
There are three points that you should remember about the of methods:
1. Indexing for month parameter starts from 1. In other words, to specify January, you must pass 1 (or use the enum valueMonth.JANUARY). 2. They use a 24 hour clock for the hour parameter. Thus, to specify 11 AM, you need to pass 11 and to specify 11 PM, youneed to pass 23. 3. They throw java.time.DateTimeException (which extends java.lang.RuntimeException and is, therefore,an unchecked exception) if the value passed for any field is out of range. For example, LocalDate.of(2024, 2, 29);will throw a DateTimeException because February of 2018 doesn't have 29 days. Similarly, LocalTime.of(24,10); will also throw a DateTimeException because the range of the hour parameter is only 0 to 23.
The Period class has the following of methods: static Period of(int years, int months, int days)static Period ofDays(int days)static Period ofMonths(int months)static Period ofWeeks(int weeks)static Period ofYears(int years)
Here are a few examples that show how they can be used:
out.print(Period.ofDays(40)); //prints P40Dout.print(Period.ofMonths(-2)); //negative values are also acceptable. prints P-2Mout.print(Period.of(0, 1, 10); //prints P1M10D 
Note that a Period of 40 days is not the same as a Period of 1 month and 10 days because 1 month is not always equal to 30days.
The Duration class has similar of methods: 
System.out.println(Duration.ofDays(1)); //prints PT24H System.out.println(Duration.ofHours(24)); //prints PT24H System.out.println(Duration.of(24, ChronoUnit.HOURS)); //prints PT24H
The from methods
The from methods are similar to the of methods except that instead of specifying a value for each property individually, youspecify another TemporalAccessor object. This TemporalAccessor object is used as a source for all properties that arerequired to create the desired object. For example:
LocalDateTime ldt = LocalDateTime.now(); LocalDate ld1 = LocalDate.from(ldt); LocalTime lt = LocalTime.from(ldt); OffsetDateTime odt1 = OffsetDateTime.from(ZonedDateTime.now()); 
Observe that a LocalDateTime has a date as well as a time component and therefore, it is possible to use a LocalDateTimeto create a LocalDate as well as a LocalTime. But it is not possible to use a LocalDate to create a LocalDateTime or aLocalTime because LocalDate does not have a time component. Similarly, you can't create a ZonedDateTime using aLocalDateTime because LocalDateTime doesn't have zone information. Thus, the following code will throw aDateTimeException at run time:
LocalDate ld = LocalDate.now(); LocalDateTime ldt = LocalDateTime.from(ld); //DateTimeException at run time LocalTime lt = LocalTime.from(ld); //DateTimeException at run time ZonedDateTime zdt = ZonedDateTime.from(LocalDateTime.now()); //DateTimeException at run 
Similarly, you can create a Period using another Period but you can't create a Period using a Duration becauseDuration deals with hours, minutes, and seconds, while Period needs days, months, and years. Creating a Duration from aPeriod won't work either.
Using the plus/minus/with/at/truncatedTo instance methods
Remember that all date/time objects are immutable and therefore, you cannot change them. But you can use the values from anexisting date/time to build a new date/time object. This is helpful when the new object that you want to create is slightly differentfrom an existing object. For example, you may already have a LocalDate and you want to create a LocalDateTime by addinga time component to the same date, or you have a LocalDateTime and you want just a LocalDate, or you have a LocalDatefor today and you want a LocalDate for tomorrow. The API provides several methods for this purpose. 
To make them easy to remember, they can be categorized on the basis of how they alter the existing values:
1. methods that return a new object by altering a field of another object - plus/minus/with/truncatedTo2. methods that return a new object by adding or removing a field to an another object - at/truncatedTo
1. Instance methods that alter an existing field value
The plus/minusXXX methodsBoth - a LocalDate and a Period - have three components: day, month, and year. To modify any of these properties of, you have
plusDays, plusWeeks, plusMonths, and plusYears and minusDays, minusWeeks, minusMonths, andminusYears methods in LocalDate as well as in Period. Similarly, LocalTime has plusHours, plusMinutes,plusSeconds, plusNanos and minusHours, minusMinutes, minusSeconds, minusNanos methods to modify theproperties that it supports.
Note that LocalTime does not have methods to alter the day, month, and year because LocalTime does not have theseproperties, while LocalDateTime has plus and minus methods for all properties of LocalDate as well as LocalTime.
Example:
LocalDate ld1 = LocalDate.now(); LocalDate ld2 = ld1.plusDays(10); Period p = Period.ZERO.plusDays(10); 
The plusXXX and minusXXX methods take only one argument because the name of the property to be updated is implied by theirnames. 
There are four more plus and minus methods that do the same thing but in a different way - plus(long amountToAdd,TemporalUnit unit), plus(TemporalAmount amountToAdd), minus(long amountToSubtract,TemporalUnit unit), minus(TemporalAmount amountToSubtract). These methods identify the property to bealtered through the arguments that are passed to them.
Example:
LocalDate ld1 = LocalDate.now(); LocalDate ld2 = ld1.plus(10, ChronoUnit.DAYS);//add 10 days LocalDate ld3 = ld1.minus(Period.of(0, 0, 10));//subtract 0 yrs, 0 months, 10 days LocalDate ld4 = ld1.plus(Period.ofDays(-10));//add -10 days, i.e., subtract 10 days
Remember from the class hierarchy diagram that I showed earlier that Period implementsTemporalAmount and ChronoUnit is an enum that implements TemporalUnit.
You need to be careful about using days and months while manipulating dates. Adding a month to a date is not the same as adding 30days to the date because the number of days in a month depends on the month of the date that you want to manipulate. The followingexample shows the difference:
LocalDate ld = LocalDate.of(2024, 01, 31); LocalDate ld1 = ld.plusDays(30); System.out.println(ld1); //prints 2024-03-02 LocalDate ld2 = ld.plus(Period.ofMonths(1)); System.out.println(ld2); //prints 2024-02-29
If you try to add to or subtract from a field that is not supported by a particular class, a DateTimeException will be thrown. Forexample, adding hours to a LocalDate or adding months to a LocalTime, will throw a DateTimeException at runtime. 
The withXXX methodsIf you want to specify an exact value for a property instead of adding to or subtracting from a property, you can use the withXXXmethods.
Example:
LocalDate ld = LocalDate.now();//doesn't matter what the year is now LocalDate ld2 = ld.withYear(2025);//change year to 2025 ld2 = ld.withMonth(2);//change month to Feb ld2 = ld.withDayOfMonth(4);//change date to 4 LocalDateTime ldt = LocalDateTime.now(); ldt = ldt.withYear(2019);//change year to 2019 ldt = ldt.withHour(23);//change hour to 23
Period has similar withXXX methods exception that the names of the methods end with an 's':
Period p1 = Period.ZERO.withDays(10); p1 = p1.withMonths(2); p1 = p1.withYears(1); //p1 now points to a Period with 1 year, 2 months, and 10 days
Period also has a negated method that returns a new Period with amount for each component negated. For examplePeriod.of(1, 3, 20).negated(); returns a Period of -1 year, -3 months, and -20 days. Duration has similarwith and negated methods.
2. Instance methods that add new properties or remove properties to/from an existing object - at and truncatedTo
The atXXX methodsWhat if you have a LocalDate and you want a LocalDateTime by adding a time component to the existing date?Well, LocalDate has several atTime methods that let you create a LocalDateTime using a LocalDate.
Example:
LocalDate ld = LocalDate.now(); LocalDateTime ldt = ld.atTime(10, 15); //same date with 10hr 15mins ldt = ld.atTime(10, 15, 45); //same date with 10hr 15mins 45 secs.
Similarly, LocalTime has atDate(LocalDate ld), which returns a LocalDateTime and LocalDateTime hasatZone(ZoneId id), which returns a ZonedDateTime.
LocalTime lt = LocalTime.now(); LocalDate ld = LocalDate.now(); LocalDateTime ldt = lt.atDate(ld); //add a LocalDate to LocalTime.
Note that LocalDateTime does not have atTime or atDate because LocalDateTime already has a time as well as a datecomponent. But it does not have an offset or a zone. So, LocalDateTime does have atOffset and atZone methods:
ZonedDateTime zdt = LocalDateTime.now().atZone(ZoneId.of("America/New_York"));

Creating a Date/Time object using the static parse methods
All date/time classes have two parse methods that return an object of the respective class using information present in the stringargument. For example, LocalDate has the following two methods: 
static LocalDate parse(CharSequence text)static LocalDate parse(CharSequence text, DateTimeFormatter formatter)These are quite straight forward to use:
LocalDate ld = LocalDate.parse("2018-02-14"); LocalTime lt = LocalTime.parse("22:10:30"); LocalDateTime ldt = LocalDateTime.parse("2018-02-14T18:12:12"); 
The string that you pass must contain date/time data in a specific format. This format is described by an object of classjava.time.format.DateTimeFormatter. 
A DateTimeFormatter object understands the format in which date/time information is present in a string. While it is possibleto design your own format for writing a date, standard formats for writing the date/time strings exist, and DateTimeFormatterclass provides several readymade DateTimeFormatter objects that understand these standard formats. These object can beaccessed through public static variables of DateTimeFormatter class. You need to be aware of three such variables -ISO_LOCAL_DATE, ISO_LOCAL_TIME, and ISO_LOCAL_DATE_TIME - because when you don't pass a formatter to theLocalDate/Time's parse methods, these are the formatters that the parse methods use internally to parse the string. LocalDate usesISO_LOCAL_DATE, LocalTime uses ISO_LOCAL_TIME, and LocalDateTime uses ISO_LOCAL_DATE_TIME to parsethe given string. Thus, for example, invoking LocalDate.parse("2024-02-14"); will produce the same result asinvoking LocalDate.parse("2024-02-14", DateTimeFormatter.ISO_LOCAL_DATE);
For the purpose of the exam, you only need to know that ISO_LOCAL_DATE expects strings in yyyy-MM-ddformat, ISO_LOCAL_TIME expects strings in HH:mm or HH:mm:ss format, and ISO_LOCAL_DATE_TIME expectsstrings in yyyy-MM-ddTHH:mm:ss or yyyy-MM-ddTHH:mm format (ignoring the nano second part of the timecomponent), where yyyy stands for four digit year, MM stands for two digit month, dd stands for two digit date, HHstands for two digit hour, mm stands for two digit minute, and ss stands for two digit second. You will not berequired to parse complicated strings in the exam. 
Furthermore, unless the problem statement says otherwise, you should answer the question assuming that thecode is executed with English/US as its language. Therefore, the names and short codes of the months would bein English.
Similarly, OffsetDateTime's parse methods use DateTimeFormatter.ISO_OFFSET_DATE_TIME by default,ZonedDateTime's parse methods use DateTimeFormatter.ISO_ZONED_DATE_TIME and so on. You do not need toknow the formatting details of these formatters, but you do need to know that they exist so that you won't assume an option to beincorrect just because it uses one of these formatters.
The DateTimeFormatter class
Creating a DateTimeFormatter to parse a non-standard string is also quite easy. DateTimeFormatter has a staticofPattern(String pattern)method and a static ofPattern(String pattern, String locale) method thattake the format specification as an argument. For example, if your dates are in MMM/dd/yy format, you can create a formatter likethis:
DateTimeFormatter dtf = DateTimeFormatter.ofPattern("MMM/dd/yy"); LocalDate ld = LocalDate.parse("Oct/23/19", dtf);//assuming English/US System.out.println(ld);//prints 2019-10-23
Format specification uses predefined characters to denote various components of a date/time. While a detailed understanding of thisspecification is not required, you should be aware of the meaning of a few basic letters:
y is for yearM is for monthd is for day of monthH is for hour of day m is for minutes is for second n is for nanosecond
Parsing a string to create a Period or a Duration
The Period also has a parse method but the format of a period string is quite different from date/time. It looks weird to be honestwhen you look at it for the first time but it actually makes sense. It follows ISO-8601 period format and looks like this: PnYnMnDand PnW. Here, n stands for a number and P, Y, M, D, and, W are letters that appear in the string. The case of the letters is notimportant. For example, P1Y10M3d means 1 year, 10 months, and 3 days, P1Y3D means 1 year and 3 days. p1Y2w means 1 yearand 2 weeks.
It is now easy to create a Period by parsing a string. For example, Period p = Period.parse("p1Y2w"); creates a
Period with 1 year and 2 weeks. You can create a Period with negative values as well, for example, "-P2m3d" and "P-2m-3d" will be parsed into the same Period representing -2 months and -3 days.
Parsing a Duration works similarly but it uses the character T to isolate the time information in the input string:System.out.println(Duration.parse("P1DT3H4M")); //prints PT27H4M
Observe that since Duration considers 1 day as 24 hours, it prints 27H in the above output.
You will not be asked to parse a complicated string in the exam. The exam does not have trick questions in thisarea and the basic knowledge given above will be sufficient for you to answer the questions in the exam.
Reading the state of date/time objects
All date/time objects allow reading of their properties through appropriate getters. For example, JavaDoc API description forLocalDateTime lists the following getters:

Besides the above, it also has the following two special get methods:

Properties supported by Period
Period has the following getters: int getDays(): Gets the amount of days of this period.int getMonths(): Gets the amount of months of this period.int getYears(): Gets the amount of years of this period.long get(TemporalUnit unit) : Gets the value of the requested unit.
Properties supported by Duration
Since Duration models a quantity or amount of time in terms of seconds and nanoseconds, Duration does not have getHours() orgetMinutes(). It only supports getSeconds(), getNano(), and get(TemporalUnit unit) methods.
Chaining method calls
Most of the methods that you have seen thus, far for creating new date/time objects (i.e. now, of, ofXXX, from, plusXXX, minusXXXand withXXX) return a reference of the same type. That makes it easy for you to customize the object you want by chaining multiplemethod calls in one statement. For example:
LocalDate ld = LocalDate.now().withYear(2010).plusMonths(2).minusDays(10); 
First, you should get used to evaluating the result of such chained method calls because you will see such code on the exam. Second,evaluating such method calls is usually straight forward but you need to watch out for the following tricks that you will encounter inthe exam:
1. Watch out for lost objects - Since all date/time objects are immutable, none of the methods change the object they are invokedon. They return a new object. If you don't assign this new object to a variable, you won't see the result of your method calls.E.g.:
LocalDate ld = LocalDate.of(2018, 1, 1); ld.plusMonths(2).plusDays(10); System.out.println(ld); 
You should change the second line to ld = ld.plusMonths(2).plusDays(10); if you want to see 2018-03-11 inthe output. 
2. Watch out for return types - Unlike the other creation methods, the atXXX methods return a reference of a different type. Forexample, LocalDate's atTime method returns a LocalDateTime. If a call to this method is embedded in the call chain,pay close attention to the type of the reference variable to which the result is being assigned. For example, the following codewill not compile:
LocalDate ld = LocalDate.of(2018, 1, 1); ld = ld.withYear(2010).plusDays(10).atTime(10, 20).plusMonths(2); 
Observe that the of method of LocalDate is being invoked above and therefore, it returns a LocalDate. For the samereason, the call to plusDays also returns a LocalDate. But the call to atTime on a LocalDate returns aLocalDateTime and therefore, the next call to plusMonths in the chain returns a LocalDateTime. ALocalDateTime object cannot be assigned to a variable of class LocalDate. 
3. Watch out for unsupported properties - You can't add days to a LocalTime or hours to a LocalDate. Thus, while youmay be led to believe that the following code will print "2018-01-01" (if you manage to avoid the first trap) but the fact isthat it will not compile because LocalDate doesn't even have methods that alter time related fields.
LocalDate ld = LocalDate.of(2018, 1, 1); ld.plusHours(10); // will not compile System.out.println(ld); 
4. Watch out for chaining of static methods of Period - This one is better explained through code. What do you think thefollowing code will print?
LocalDate ld = LocalDate.of(2018, 1, 31).of(2019, 1, 1); System.out.print(ld+" "); Period p1 = Period.ZERO; Period p2 = p1.ofDays(1).ofMonths(1); System.out.println(p2); 
It prints - 2019-01-01 P1M. From the output, it looks like the call to ofDays(1) on p1 had no effect! Actually, the call to of(2018, 1, 31) on LocalDate had no effect either but the result produced in case of a Period ismore alarming. In both the cases, the ofXXX methods are static methods and produce a new object from scratch. Unlike the instance methods(i.e. with, plus, minus, ), the static methods (of and parse) don't build "on top of" a previous object. As you know, it istechnically valid to invoke a static method on a reference variable but invoking a static method on a reference is the same asinvoking a static method on the class name. Thus, LocalDate.of(2018, 1, 31) produces a new LocalDate instanceand chaining another of method to this LocalDate instance is actually the same as invoking LocalDate.of(2019, 1,1) independently. However, since both the calls provide values for all the fields of a LocalDate, there is no difference inthe end result. 
Similarly, in case of Period, invoking ofMonths(1) on an existing Period instance is the same as invoking
Period.ofMonths(1). However, since ofMonths method creates a Period with 0 years and 0 days, it seems as if thiscall lost the value of the days property that was set earlier through Period.ofDays(1). 
In fact, none of the static methods make use of the values of an existing date/time instance even if you invoke the static methodusing a reference instead of the class name. If you want to create a Period with 1 month and 1 day, you should usePeriod.of(0, 1, 1);.
10.3 Translating Date/time objects into different types and different time zones ☝
As explained earlier, humans cannot comprehend what "1735711200000 milliseconds since epoch" means. For example, you cannottell someone to call you at "1735711200000 since epoch" even though it is a perfectly valid specification of the time when you wantthem to call. Humans need a format such as 1st Jan 2025 6AM UTC to make sense of time. However, even a time written inthis format can be inconvenient when people are spread out geographically and are in different time zones. For example, if you are inNew York, you may be befuddled if you are asked to dial in for a team meeting at 2PM UTC on 29th March 2024! You wouldexpect to see the time in your time zone, i.e., 10AM EST.
Java's Date/Time API makes it quite easy to do these translations. One way to capture a date/time at a zone is to create aZonedDateTime using LocalDateTime and the time zone that you want. Like this:
LocalDateTime ldt = LocalDateTime.of(2024, 04, 29, 10, 0, 0); //no time zone here ZonedDateTime nyTime = ldt.atZone(ZoneId.of("America/New_York")); //time in New York, 20
To see the same time in another time zone, you can do:
Instant ins = nyTime.toInstant(); //get the time on machine's time line, i.e., UTC ZonedDateTime indiaTime = ins.atZone(ZoneId.of("Asia/Calcutta")); //translate it to the 
Or you can use the ZonedDateTime's withZoneSameInstant method to do it in one call:ZonedDateTime indiaTime = nyTime.withZoneSameInstant(ZoneId.of("Asia/Calcutta"));
Both the approaches will set indiaTime to 2024-04-29T19:30+05:30[Asia/Calcutta].
Translating between ZonedDateTime and OffsetDateTimeSince ZonedDateTime and OffsetDateTime both contain a zone id (remember that ZoneOffset extends ZoneId), it ispossible to translate either of these two types to the other. However, recall that the ZoneId of an OffsetDateTime does notreally correspond to an actual region. It just contains the offset amount (such as "-4:00"). Translating a ZonedDateTime to anOffsetDateTime will lose the region information while keeping the offset amount. Therefore, convertingthat OffsetDateTime back to the same ZonedDateTime will not be possible as shown by the following code:
ZoneId nyZone = ZoneId.of("America/New_York"); ZonedDateTime nyZdt = ZonedDateTime.of(LocalDateTime.of(2024, 5, 1, 6, 0, 0), nyZone); System.out.println(nyZdt); //prints 2024-05-01T06:00-04:00[America/New_York] OffsetDateTime nyOdt = nyZdt.toOffsetDateTime(); System.out.println(nyOdt); //prints 2024-05-01T06:00-04:00 ZonedDateTime newZdt = nyOdt.toZonedDateTime(); System.out.println(newZdt); //prints newzdt = 2024-05-01T06:00-04:00
Observe that there is no region information in the ZonedDateTime instance that was created from the OffsetDateTimeinstance. Since this ZonedDateTime instance does not have any region information, it can't apply rules for DST. This is proven bythe following code:
System.out.println(nyZdt.plusMonths(7)); //prints 2024-12-01T06:00-05:00[America/New_YorSystem.out.println(newZdt.plusMonths(7)); //prints 2024-12-01T06:00-04:00
You can see that the the time zone offset for the new ZonedDateTime created from nyZdt changed from -4 to -5 (because DSTends on 3rd Nov 2024) upon adding 7 months to it but it did not change for newZdt because even though a ZonedDateTimeknows how to handle DST, it can do so only if it is created with an official ZoneId.
Translating from ZonedDateTime and OffsetDateTime to InstantSince an Instant corresponds to a time in UTC (which has 0 offset), translating a ZonedDateTime or a OffsetDateTimeto an Instant is possible and just requires the offset amount of these types to be subtracted from the time that they contain. Forexample, a ZonedDateTime of 2024-12-01T06:00-05:00[America/New_York] will translate to an Instantrepresenting 2024-12-01T11:00Z (because 6 - -5 = 11). Similarly, a ZonedDateTime of 2024-04-29T19:30+05:30[Asia/Calcutta]will translate to an Instant representing 2024-04-29T14:00:00Z (because19:30 - 5:30 = 14:00). 
However, an Instant cannot be translated to a ZonedDateTime or an OffsetDateTime because it wouldn't know whatzone id or offset amount to use for the translation. Of course, you can create them from an Instant by providing a ZoneId or aZoneOffset. For example: instant.atZone(ZoneId.of("America/New_York") orinstant.atOffset(ZoneOffset.ofHoursMinutes(1, 20)).
10.4 Working with Daylight savings time ☝
Note: If you have no idea about Daylight Savings Time, it would be better if you read a few basic articles on it before reading thissection. You may start with this Wikipedia page: https://en.wikipedia.org/wiki/Daylight_saving_time 
In the previous section you saw that 10AM on 29th April 2024 in New York was translated to 7.30PM in India. Normally,Eastern Time (ET) is 5 hours behind UTC but on 29th Apr 2024, Daylight Savings Time (DST) was in effect in ET (whichmeans, the clocks had already been shifted 1 hour forward in New York) and so, ET was only 4 hours behind UTC on this date. Indiadoes not observe DST and so, Indian Standard Time (IST) is always 5.30 hours ahead of UTC. You may verify these numbers byprinting nyTime.getOffset() and indiaTime.getOffset(). They will print -04:00and +05:30 respectively. That iswhy the 10AM in ET was translated to 7.30PM in IST instead of 8.30PM on this day. This example shows that ZonedDateTimehandles the adjustments required due to DST automatically.
Note that I have used ET and IST only for illustrating the logic. You do not need to remember the offsets for anytime zone or the dates and the amount of shift required due to DST for any location. 
In the real exam, the problem statement will include this information if it is needed to arrive at the correct answer.
Translating into gaps and overlaps created due to DST
The translation from ET to IST was easy, but what if, after the translation, the date and time at the target location doesn't exist? Thiscould happen when the target location observes DST and the translated date/time happens to fall at the time when the clocks havebeen moved forward. For example, given that ET is 5 hours behind UTC and the DST starts on 10th March 2024 at 2AM (thismeans, as soon as the clocks in New York hit 2AM on this day, they are moved forward by 1 hour to show 3AM), what if you try toconvert 10th March 2024 7.30AM UTC to ET? Normally, the time in ET would be 2.30AM but on 10th March 2024,2.30AM doesn't exist in ET!
LocalDateTime ldt = LocalDateTime.of(2024, 03, 10, 7, 30, 0); //10th March 2024 7.30 AM ZonedDateTime utcTime = ldt.atZone(ZoneId.of("Z")); //Z implies UTC ZonedDateTime nyTime = utcTime.withZoneSameInstant(ZoneId.of("America/New_York")); System.out.println(nyTime); 
The above code prints 2024-03-10T03:30-04:00[America/New_York], which shows that Java automatically moves thetime forward to 3.30AM and the zone offset to -4 due to DST when the time at the destination falls into the gap. 
The reverse happens when DST ends. The clocks are shifted back by 1 hour. So, for example, since DST ends at 2AM on 3rd Nov2024 in New York, as soon the clocks hit this date/time, they are moved back to 1AM. Thus, people in New York get to live the hourbetween 1AM to 2AM twice on that day! During the first hour the Zone offset is -4 (because DST was in place at that time) and duringthe second hour, it is -5. This sounds cool but what happens when a time from another time zone that doesn't observe DST during thisperiod is translated to New York time? 
Let's work it out with the same two time zones - UTC and ET. Imagine that you are translating the time continuously from 4AM UTConwards to ET. Translating any time before 5AM UTC to ET is easy. Since DST is "ON" in ET during that period, the time in ET
would just be UTC minus 4 (instead of UTC minus 5). So, 5AM UTC would be 1AM ET, no doubt. During the time between 5AMUTC (inclusive) and 6AM UTC(exclusive), the DST is still ON because the clocks in ET haven't hit 2AM yet. Thus, the timesbetween 5AM UTC (inclusive) and 6AM UTC (exclusive) map to 1AM ET (inclusive) to 2AM ET (exclusive) with an offset of -4.Now, the clocks in ET hit 2AM and the time in ET shifts back to 1AM. Therefore, 6AM UTC also maps to 1AM ET but with an offsetof -5. Observe that two time periods in UTC (5AM to < 6AM and 6AM to <7AM) map to the same time period in ET (1AM to <2AM)but with different offsets. The following code bears this out:
ZoneId zUTC = ZoneId.of("GMT+0"); LocalDate ld = LocalDate.of(2024, 11, 3); LocalTime lt1 = LocalTime.of(5, 0, 0); LocalTime lt2 = LocalTime.of(6, 0, 0); ZonedDateTime timeInUTC1 = ZonedDateTime.of(ld, lt1, zUTC); ZonedDateTime timeInUTC2 = ZonedDateTime.of(ld, lt2, zUTC); ZoneId zNY = ZoneId.of("America/New_York"); ZonedDateTime timeInNY1 = timeInUTC1.withZoneSameInstant(zNY); ZonedDateTime timeInNY2 = timeInUTC2.withZoneSameInstant(zNY); System.out.println(timeInNY1); //2024-11-03T01:00-04:00[America/New_York] System.out.println(timeInNY2); //2024-11-03T01:00-05:00[America/New_York]
Observe that even though the time in both the cases is 1AM, the offsets are -4 and -5. Therefore, translating these date/times back toUTC will give you 5AM UTC and 6AM UTC respectively. 
Another example:
//Given that DST starts on 2AM, 9th March 2025 and ends on 2AM, 2nd Nov 2025 ZoneId ny = ZoneId.of("America/New_York"); LocalTime lt = LocalTime.of(1, 10); ZonedDateTime zdt1 = ZonedDateTime.of(LocalDate.of(2025, 3, 9), lt, ny); ZonedDateTime zdt2 = zdt1.plusHours(1); System.out.println(zdt1.getHour()+ "/"+ zdt1.getOffset()); //prints 1/-5 System.out.println(zdt2.getHour()+ "/"+ zdt2.getOffset()); //prints 3/-4 ZonedDateTime zdt3 = ZonedDateTime.of(LocalDate.of(2025, 11, 2), lt, ny); ZonedDateTime zdt4 = zdt3.plusHours(1); System.out.println(zdt3.getHour()+ "/"+ zdt3.getOffset());//prints 1/-4 System.out.println(zdt4.getHour()+ "/"+ zdt4.getOffset());//prints 1/-5
10.5 Comparing date/time objects ☝
There are four ways to compare date/time objects.
1. Using the equals method - All date/time classes override the equals method to compare the contents of the two objects.They only return true if the argument is an object of the same class and their contents match exactly.
LocalDate ld1 = LocalDate.now();//assuming today is 2024-04-30 LocalDate ld2 = LocalDate.parse("2024-04-30"); System.out.println(ld1.equals(ld2)); //prints true LocalDateTime ltd = LocalDateTime.now(); System.out.println(ltd.equals(ld2)); //prints false
Recall that the signature of equals is equals(Object obj), therefore, there is no compilation error when you pass anobject of a different class to equals. 
2. Using the compareTo method - All date/time classes implement java.util.Comparable interface, which has acompareTo method. Unlike the equals method, this method returns an int. If the date/time passed in the argument is later,this method returns a negative number, if the argument is exactly same, this method returns 0, and a positive number otherwise.
LocalDateTime ltd1 = LocalDateTime.now();//assuming today is 2024-04-30 LocalDateTime ltd2 = LocalDateTime.parse("2024-05-30T10:20"); 
System.out.println(ltd1.compareTo(ltd2)); //prints -1 LocalDateTime ltd3 = LocalDateTime.parse("2024-03-30T10:20"); System.out.println(ltd1.compareTo(ltd3)); //prints 1
One might expect that the return value would be the difference between the two dates, but the JavaDoc API description for thismethod does not make any such promise. Thus, you should rely only on the sign of the return value and not on the actual value. 
3. Using the isAfter/isBefore methods - As their names suggest, these methods check if this date is after or before thedate/time passed in the argument.
LocalDate ld1 = LocalDate.now();//assuming today is 2024-04-30 LocalDate ld2 = LocalDate.parse("2024-04-29"); System.out.println(ld1.isAfter(ld2)); //prints true System.out.println(ld1.isBefore(ld2)); //prints false Instant now = Instant.now(); Instant oneHrLater = now.plus(1, ChronoUnit.HOURS); System.out.println(oneHrLater.isAfter(now)+" "+oneHrLater.isBefore(now)); //prints tr
The type of the argument must be the same as the type of the object on which these methods are called. So, for example, astatement such as zonedDateTime.isAfter(localDateTime) will not compile. 
Determining the result of isAfter/isBefore is easy when the dates being compared are in the same time zone but can getvery confusing when they are not. For example, can you tell what the following code will print?
LocalDateTime someDate = LocalDateTime.of(2025, 1, 1, 10, 0, 0); //1st Jan 2025 10 AMZonedDateTime zJohn = someDate.atZone(ZoneId.of("America/New_York")); //zone offset iZonedDateTime zJane = someDate.atZone(ZoneId.of("Asia/Calcutta")); //zone offset is +System.out.println(zJohn.isAfter(zJane)); 
Don't feel bad if you don't get this. The way to do this is to first get the two dates on to a common time line, i.e., UTC. You sawhow to do that in the previous section. zJohn translated to UTC is 2025/1/1 15:00 (10 - -5 = 15) and zJane translatedto UTC is 2025/1/1 04:30 (10 - 5.30 = 4.30). It is now easy to see that zJohn is after zJane (because 15:00 is after04:30) and so, the statement will print true. 
4. Using the isEqual method - This method is provided only by LocalDate and LocalDateTime. It checks if this date isequal to the date passed in the argument.
LocalDate ld1 = LocalDate.now();//assuming today is 2018-04-30 LocalDate ld2 = LocalDate.of(2018, 4, 29); System.out.println(ld1.isEqual(ld2)); //prints false System.out.println(ld1.isEqual(ld1)); //prints true
Period has only three instance methods that deal with comparison - equals, isZero, and isNegative. Equals only returnstrue if all three components of the two Periods match. IsZero only returns true if all the three components of the Period arezero. IsNegative only returns true if any of the three components of the Period is less than zero. Duration has the samethree methods too for comparison and they work the same way.
10.6 Converting Date/time objects to strings ☝
You can get a string representation of a date/time object using either the toString method or theformat(DateTimeFormatter dtf) method. 
Just like the single argument parse methods, the toString method uses the ISO format for generating the string. Here are a fewexamples:
System.out.println(LocalDateTime.now()); //prints 2024-04-27T14:34:46.425524900 System.out.println(OffsetDateTime.now()); //prints 2024-04-27T14:34:46.426840800+05:30 
System.out.println(ZonedDateTime.now()); //prints 2024-04-27T14:34:46.426840800+05:30[As
Observe that the output includes a character 'T' that separates the date and the time components.
Here is an example that uses a custom DateTimeFormatter:
DateTimeFormatter dtf = DateTimeFormatter.ofPattern("yy MMM dd"); System.out.println(dtf.format(LocalDate.now())); //prints 24 Apr 27 System.out.println(dtf.format(LocalDateTime.now())); //prints 24 Apr 27
An interesting thing to note in the above output is that no exception is thrown at the second line. The pattern that we used to create theDateTimeFormatter does not include any information for time. Yet, when we used this formatter to format aLocalDateTime, it didn't complain. It simply ignored the time component of the LocalDateTime object. This is totallyopposite to how the parse method behaves. If you try to parse a string that has a time component using this formatter, it will throwan exception.
LocalDate ld = LocalDate.parse("24 Apr 27 10:10", dtf); 
The output from the above code is:
java.time.format.DateTimeParseException: Text '24 Apr 27 10:10' could not be parsed, unp
By the way, DateTimeParseException extends DateTimeException. 
Passing a string as an argument to the ofPattern method is an example of "hardcoding". If you want to standardize the format inwhich you want to print dates across your application, using a hardcoded string is not a good idea because it is prone to typos andmisunderstandings.
DateTimeFormatter provides a better way to create formatter objects through its static ofXXX methods. It has four suchmethods:
static DateTimeFormatter ofLocalizedDate(FormatStyle dateStyle) static DateTimeFormatter ofLocalizedDateTime(FormatStyle dateTimeStyle) static DateTimeFormatter ofLocalizedDateTime(FormatStyle dateStyle, FormatStyle timeStylstatic DateTimeFormatter ofLocalizedTime(FormatStyle timeStyle) 
The method that should be used depends on the kind of object you want to format. If you have a LocalDate, you should useofLocalizedDate, if you have a LocalTime, you should use ofLocalizedTime, and if you have a LocalDateTime toformat, you should use ofLocalizedDateTime to get the formatter. Using an incompatible formatter, such as using a formatterfrom ofLocalizedTime to format a LocalDateTime, will cause a DateTimeException to be thrown.
Observe that instead of accepting a string for a format, these methods accept an object of type FormatStyle. FormatStyle isactually an enum with four values - FULL, LONG, MEDIUM, and SHORT. You should use a combination of ofXXX method andFormatStyle to create a DateTimeFormatter that satisfies your needs. For example, the following code shows how you canprint a date in full as well as in short form:
DateTimeFormatter dtf1 = DateTimeFormatter.ofLocalizedDate(FormatStyle.FULL); DateTimeFormatter dtf2 = DateTimeFormatter.ofLocalizedDate(FormatStyle.SHORT); LocalDate ld = LocalDate.now(); System.out.println(dtf1.format(ld));//prints Saturday, April 27, 2024 System.out.println(dtf2.format(ld));//prints 4/27/24 
Similarly, the following code prints a LocalDateTime in short and medium forms:
DateTimeFormatter dtf1 = DateTimeFormatter.ofLocalizedDateTime(FormatStyle.SHORT); DateTimeFormatter dtf2 = DateTimeFormatter.ofLocalizedDateTime(FormatStyle.MEDIUM); LocalDateTime ld = LocalDateTime.now(); System.out.println(dtf1.format(ld)); //prints 4/27/24 1:03 PM 
System.out.println(dtf2.format(ld)); //prints Apr 27, 2024 1:03:59 PM//(Remember that the exact output depends on your default locale)
Using FormatStyle.LONG or FormatStyle.FULL for formatting a LocalDateTime or LocalTime will throw anexception at run time because these forms expect time zone information in the time component, which is not present inLocalDateTime or LocalTime. 
The exam does not expect you to remember the formats in which these formatters print the date/time. You only need to know howstandardized formatters can be created using the ofXXX methods mentioned above instead of the ofPattern methods.
Note that Period and Duration do not have any format method. To convert them into a string, you have to usetheir toString method. This method generates a string in the same ISO-8601 format that I talked about before. Here is an example:
Period p = Period.parse("p13m5w"); System.out.println(p); //prints P13M35D Duration d = Duration.parse("pt26h66m3s"); System.out.println(d); //prints PT27H6M3S
Observe that 5 weeks have been converted into 35 days but 13 months have remained unchanged. Also, 66 minutes in the givenduration string have been converted to 1 hour and 6 minutes.
